# Chat BI 落地实现方案（务实版）

> 基于 Spring Boot + Vanna 的智能 BI 系统，大模型仅负责 NL→SQL 语义翻译，所有权限控制、SQL 校验、数据安全由 Java 后端闭环处理。

---

## 一、设计原则

1. **大模型只做翻译**：Vanna 仅根据 Schema 将自然语言转为初代 SQL，不感知任何用户身份、组织架构、权限规则。
2. **安全后置但前置拦截**：SQL 生成后由 Java 端做 AST 解析与权限校验，但**列权限的主校验在 SQL 执行前完成**，结果层过滤仅作为兜底保险。
3. **不信任前端**：所有权限判定在服务端完成，前端仅做展示，不参与安全决策。
4. **可用性与安全平衡**：缓存失效时允许降级查库（带熔断/限流），不因局部故障导致全局不可用。
5. **复杂场景显式降级**：对 CTE、UNION、窗口函数等复杂 SQL 给出明确的「支持 / 拒绝 / 改写」策略，不假设所有查询都是单表或简单 JOIN。

## 三、核心控制流

### 第一步：请求入口与身份校验

1. **JWT 认证**：从 Token 解析用户 ID、租户 ID、角色列表。
2. **功能权限校验**：判定当前用户是否拥有 `chatbi:query` 功能权限，无则直接返回 `403`。
3. **上下文挂载**：将用户身份、租户 ID 写入 `ThreadLocal`，供后续链路使用。
4. **关于 MenuCode**：前端可上报当前页面编码用于审计日志和辅助路由，**但不做安全判定依据**。安全判定只依赖 Token 解析出的角色与数据权限配置。

### 第二步：Schema 上下文构建

1. **获取用户可见表清单**：根据用户角色，从权限服务查询其拥有「表级权限」的物理表列表。
2. **组装 Schema 上下文**：将这些表的完整 DDL（含所有列、索引、外键关系）拼接为字符串，作为 `schema_context`。
3. **关键策略**：
   - 不包含用户无表级权限的表（缩小 Vanna 幻觉空间）。
   - 包含的表必须给完整 DDL（包括所有列），不因列权限而裁剪 DDL，避免破坏 JOIN 条件生成。
   - 行权限规则**不写入 Schema 上下文**，避免大模型学习权限逻辑后生成带条件的 SQL。

### 第三步：Vanna 生成初代 SQL

1. 调用 Vanna 服务，传入 `question + schema_context + conversation_history`。
2. Vanna 返回初代 SQL 字符串及解释文本。
3. **Vanna 服务承诺**：不连接业务数据库，不执行 SQL，仅做文本生成。

### 第四步：SQL 元数据提取（JSQLParser AST）

将初代 SQL 解析为 AST，深度遍历提取：

| 提取目标 | 用途 |
|----------|------|
| 所有物理表名（含 JOIN、子查询、CTE 底层表） | 表级白名单校验 |
| 运行时别名 ↔ 物理表名映射 | 后续列溯源、行权限注入 |
| SELECT 列表中的底层物理列 | 列级白名单校验 |
| WHERE / JOIN ON / GROUP BY / ORDER BY / HAVING 中的列 | 列级白名单校验 |
| 子查询嵌套层级与结构 | 递归校验与注入 |
| 是否存在 `SELECT *` | 特殊处理 |

### 第五步：权限主校验（执行前硬拒绝）

**5.1 语法白名单**
- 仅允许 `SELECT` 语句。
- 禁止堆叠查询（`;` 分隔的多条语句）。
- 禁止危险函数（`BENCHMARK`, `SLEEP`, `LOAD_FILE` 等，数据库相关）。
- 子查询嵌套深度不超过配置阈值（如 3 层）。

**5.2 表级校验**
- 提取的所有物理表名必须是用户「表级权限清单」的子集。
- **失败策略**：直接拒绝，返回 `"问题涉及您无权访问的数据范围"`，不进入后续流程。

**5.3 列级校验（主链路）**
- 遍历 AST 中所有 `Column` 节点，通过「别名映射表」还原为 `物理表名.列名`。
- 校验每一个底层物理列是否在当前用户、当前页面的「列级白名单」内。
- **特殊处理**：
  - `SELECT *`：展开为表的全部列，逐一校验。若存在无权限列，**拒绝**（不自动改写为显式列，避免破坏 GROUP BY / ORDER BY 联动）。
  - 聚合函数如 `COUNT(*)`：`*` 不指向具体列，默认允许。
  - 表达式列如 `price * quantity AS total`：校验底层列 `price` 和 `quantity`，任一缺失则拒绝。
- **失败策略**：直接拒绝，不执行 SQL。

> **原则**：列权限在 SQL 执行前必须校验通过。结果层过滤仅作为「兜底保险」，防止 AST 解析遗漏或边界场景穿透。

### 第六步：行权限注入（RLS）

**6.1 规则获取**
- 以 `[用户ID + 租户ID + 物理表名]` 为 Key，查询 Caffeine 本地缓存 → Redis 分布式缓存。
- 缓存中存储的是结构化行规则树（JSON），不含动态值。

**6.2 规则计算**
- 使用 `SimpleEvaluationContext` 只读沙箱计算 SpEL 表达式，将 `#user.deptId` 等占位符解析为具体值。
- 沙箱关闭反射和系统调用权限。

**6.3 SQL 注入**
- 根据「别名 ↔ 物理表」映射，将行条件挂载到对应表的 WHERE 或 JOIN ON 子句。
- **单表**：直接追加到主查询 WHERE。
- **多表 JOIN**：为每个有行权限的表单独追加条件（如 `o.dept_id IN (101,102)`）。
- **子查询**：递归注入子查询的 WHERE。
- **CTE（WITH）**：注入到 CTE 定义中的底层物理表。
- **OR 条件防护**：原始 WHERE 用括号包裹后再 AND 行权限条件，防止 `OR 1=1` 绕过。

### 第七步：安全加固执行

1. **强制 LIMIT 注入**：如果 AST 中无 `LIMIT` / `TOP` / `ROWNUM` 等分页限制，根据配置自动追加（如 `LIMIT 10000`），防止全表扫描拖垮数据库。
2. **只读数据源**：使用只读账号连接数据库，禁止 DML。
3. **执行超时**：设置 SQL 执行超时（如 30 秒），超时强制中断。

### 第八步：结果集兜底过滤

数据库返回 `List<LinkedHashMap<String, Object>>`。

1. **快速短路**：若当前用户无列黑名单（或超级管理员），直接透传，不做遍历。
2. **兜底遍历**：仅在 AST 列校验阶段标记了「存在别名可能穿透」或「使用了通配列」时激活。
3. **过滤策略**：
   - **完全禁止（DENY）**：`map.remove(key)`，该列从当前行剔除。
   - **脱敏（MASK）**：`map.put(key, mask(value))`，如手机号 `138****5678`。
4. **性能认知**：遍历有开销，但属于兜底路径，主链路已通过 AST 拦截大部分风险。实际压测确定性能基线，不宣称"零 GC"。

### 第九步：返回与审计

1. 结果序列化为 JSON 返回前端。
2. 记录审计日志：用户 ID、问题文本、初代 SQL、改写后 SQL、涉及表、执行耗时、结果行数、状态（成功/拒绝/异常）。

## 四、权限安全体系

### 4.1 权限模型

```
用户 → 角色 → 数据权限组
              ├── 表级权限：允许访问的物理表清单
              ├── 列级权限：表 → 允许/禁止/脱敏 的列清单
              └── 行级权限：表 → SpEL 规则树（如 dept_id IN (#user.deptIds)）
```

### 4.2 行权限规则设计

| 规则属性 | 说明 |
|----------|------|
| `tableName` | 作用的物理表，`*` 表示通配所有表（如多租户 `tenant_id`） |
| `conditionTemplate` | SpEL 模板，如 `dept_id IN (#user.deptIds)` |
| `priority` | 规则优先级，通配规则低优先级，具体表规则高优先级 |

**注入优先级**：
1. 先应用具体表的行规则。
2. 再应用通配规则（如 `tenant_id = #user.tenantId`）。
3. 同一表的多条规则用 `AND` 连接。

### 4.3 列权限状态

| 状态 | 行为 |
|------|------|
| `ALLOW` | 正常返回 |
| `DENY` | AST 阶段校验拒绝；若穿透到结果层则 remove |
| `MASK` | AST 阶段标记；结果层执行脱敏函数 |

## 五、复杂 SQL 场景策略

不假设所有查询都是单表或简单 JOIN，对以下场景给出显式策略：

| 场景 | 策略 | 说明 |
|------|------|------|
| **单表 / 简单 JOIN** | ✅ 完全支持 | 主链路覆盖 |
| **多表 JOIN（>3 张表）** | ✅ 支持 | 行权限逐表注入，列权限逐列校验 |
| **子查询（WHERE / FROM / SELECT）** | ✅ 支持 | 递归 AST 注入与校验 |
| **CTE（WITH 子句）** | ⚠️ 有限支持 | 注入到 CTE 的底层物理表；若 CTE 嵌套过深（>2 层）建议拒绝 |
| **UNION / UNION ALL** | ⚠️ 有限支持 | 要求各分支 SELECT 列数、列别名一致；结果层以第一个分支的别名做过滤基准 |
| **窗口函数** | ⚠️ 谨慎支持 | `PARTITION BY` / `ORDER BY` 中的列需有列权限；`SELECT` 中的窗口表达式需能溯源到底层列 |
| `SELECT *` | ⚠️ 有限支持 | 优先拒绝；若业务必须，AST 展开后逐一校验列权限，任一缺失则拒绝 |
| **存储过程 / 动态 SQL** | ❌ 拒绝 | 直接返回不支持 |
| **堆叠查询（多条语句）** | ❌ 拒绝 | 直接返回不支持 |

> **降级策略**：对于有限支持的场景，若 AST 解析无法安全注入或校验成本过高，直接拒绝并提示 `"当前问题涉及复杂查询结构，请简化或联系管理员"`，不冒险放行。

## 六、缓存与可用性设计

### 6.1 两级缓存架构

| 层级 | 存储内容 | 过期策略 |
|------|----------|----------|
| **L1: Caffeine** | 用户权限规则快照（表级、列级、行规则树） | 写入后 10 分钟过期，软引用允许 GC 回收 |
| **L2: Redis** | 角色-权限映射、规则元数据 | 持久化，变更时主动失效 |

### 6.2 缓存预热与更新

1. **登录预热**：用户登录时，将其角色对应的权限规则批量加载到 Redis。
2. **运行时加载**：首次查询时，从 Redis 加载到 Caffeine。
3. **变更同步**：管理员修改权限后，更新数据库，删除 Redis 对应 Key，通过 Redis Pub/Sub 广播失效消息，各节点清除本地 Caffeine 缓存。

### 6.3 缓存击穿处理（务实版）

- **Redis 未命中**：允许同步查询权限数据库（非业务数据库），获取规则后回填 Redis。
- **防护措施**：
  - 对权限数据库查询加**分布式锁**（Redis SETNX），防止并发穿透。
  - 对权限数据库查询做**熔断**（如 10 秒内失败率 > 50% 则快速失败）。
  - 极端情况下（权限库也不可用），返回 `"系统繁忙，请稍后重试"`，而非 `AND 1=0` 返回空数据。
- **原则**：权限规则变更频率极低，同步查库的开销可接受；可用性不应为极端安全假设牺牲。

### 6.4 数据源路由

- 根据 SQL 涉及的主表，路由到对应的**只读数据源**。
- 所有数据源账号均为只读权限，无 DML 权限。

## 七、Schema 管理与 Vanna 集成

### 7.1 DDL 来源

Vanna 的 `schema_context` 不直接查业务库，而是来自：

1. **元数据服务**：独立维护的 Schema 元数据库（或从业务库同步的元数据表），包含表名、列名、类型、注释、外键关系。
2. **脱敏策略**：元数据中的敏感表（如用户密码表）在元数据层就被排除，不进入任何用户的可见表清单。

### 7.2 Schema 更新机制

| 触发条件 | 动作 |
|----------|------|
| 业务库表结构变更（DDL） | 监听 Binlog 或定时 Diff，更新元数据库，重新训练 Vanna 对应表的向量 |
| 新增业务表 | 管理员在后台配置表级可见性后，自动同步 DDL 到 Vanna 训练集 |
| 多租户场景 | 每个租户拥有独立的 Vanna 向量集合（或 Schema 前缀隔离），防止跨租户 Schema 污染 |

### 7.3 Vanna 训练数据管理

| 数据类型 | 内容 | 维护方式 |
|----------|------|----------|
| DDL | 可见表的 CREATE TABLE 语句 | 自动同步 |
| 业务文档 | 字段业务含义、枚举值说明 | Admin 后台人工维护 |
| SQL 示例 | 高频查询的 Question-SQL 对 | 用户反馈 + 运营审核入库 |

> **重要**：Vanna 的向量库中只存储「公共 Schema + 业务文档 + 示例 SQL」，**不存储任何用户身份、权限规则、组织架构信息**。

## 八、审计与监控

### 8.1 审计日志内容

```
- 用户 ID、租户 ID、角色
- 自然语言问题原文
- Vanna 返回的初代 SQL
```

## 九、风险与边界

| 风险点 | 现状 | 缓解措施 |
|--------|------|----------|
| Vanna 生成语法错误 SQL | JSQLParser 解析失败 | 返回错误提示，记录日志，不执行 |
| Vanna 引用已删除/重命名的列 | AST 列校验时无法匹配元数据 | 元数据同步延迟控制在分钟级；若列不存在于元数据，按无权限处理 |
| 复杂表达式列溯源失败 | `SELECT func(a, b) AS x` 难以精确溯源 | 保守策略：溯源失败时，要求 `a` 和 `b` 均有权限；仍失败则拒绝 |
| 行权限注入导致 SQL 性能劣化 | 注入的 IN 条件可能命中大数据量 | 行规则计算结果集大小限制（如 IN 列表不超过 1000 个值），超限改用子查询或临时表 |
| 结果集过大 | 即使加了 LIMIT，聚合前数据量仍可能很大 | 强制 LIMIT + 执行超时 + 数据库侧资源组限流 |
| 多租户 Schema 隔离失效 | Vanna 向量库未隔离 | 按租户隔离向量集合，或租户前缀强制校验 |

---

## 十、总结

本方案的核心是**「生成后置、校验前置、过滤兜底」**：

1. **Vanna 生成 SQL** 后，Java 端通过 JSQLParser 做 AST 级别的表校验、列校验、行权限注入。
2. **列权限的主拦截在 SQL 执行前**：发现无权限列直接拒绝，不依赖结果层过滤。
3. **结果层过滤**仅作为兜底保险，处理 AST 边界遗漏或 `SELECT *` 穿透场景。
4. **缓存失效时允许降级查库**，通过分布式锁和熔断保护权限数据库，不直接返回空数据牺牲可用性。
5. **复杂 SQL 场景给出明确的有限支持策略**，不假设所有查询都是简单单表，也不过度承诺全覆盖。

整套方案在安全性与可用性之间取务实平衡，工程落地成本可控，适合作为生产级 Chat BI 的基线架构。
