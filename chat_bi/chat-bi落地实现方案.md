在 **Vanna 2.0 (Text-to-SQL)** 大模型智能 BI 场景下，大模型天然的“幻觉”和随机改名（别名污染）会直接导致传统安全框架失效。我们最终沉淀并推演出的方案，是将大模型作为“纯语义翻译器”，而将**行权限（RLS）安全追加**与**列权限动态清洗**这两道最硬核的防线，牢牢卡在后端的 **Spring 框架 + 内存双级缓存** 中。

以下是对整套“中量级、高性能、防幻觉”智能 BI 数据权限方案的全栈详细总结：

------

一、 核心解耦思路：大模型负责效率，Spring 负责安全

- **Vanna 2.0 只做语义翻译**：大模型仅根据表结构（Schema）和提问意图，将自然语言翻译成标准的“初代 SQL”（不夹杂任何用户组织架构或身份逻辑），随后将 SQL 纯文本返回给 Spring。
- **Spring 承接动态安全裁剪**：Spring 接收到初代 SQL 字符串后，通过 **JSQLParser** 语法树工具在底层无感追加行权限（RLS）；在数据库执行完毕返回结果集（`List<Map>`）后，通过 **AOP 切面**进行动态列清洗。

------

二、 核心控制流的详细流转全全步骤

第一步：多维上下文上报与防篡改校验（HTTP 链路层）

1. **动态抓取**：前端（如 Axios 拦截器）在用户点击提问的瞬间，自动从当前 Vue/React 路由节点动态获取菜单编码，作为自定义请求头（如 `X-Menu-Code: order:audit`），连同用户 Token 发送给 Spring。
2. **安全常驻**：Spring 拦截器统一捕获该 `X-Menu-Code`，并塞入线程独立的异步安全存储空间（`ThreadLocal`）中。
3. **横向防篡改**：在把问题交给大模型前，安全中间件在内存中比对 `【当前用户角色集】 -> 【请求头的 MenuCode】 -> 【当前调用的 API 路由】` 的绑定关系。若不合法，判定为越权探测，直接返回 `403 Forbidden`。

第二步：行权限（RLS）动态追加与别名反向追溯（持久层重写）

当 Vanna 返回初代 SQL 字符串后，Spring 的 SQL 语法重写组件激活：

1. **JSQLParser 树状剥离**：将初代 SQL 转为抽象语法树（AST），深层遍历 `FROM` 和 `JOIN` 子句，在内存中瞬间建立一个**【物理表名 ── 运行时别名】的临时对照表**。系统得知：别名 `o` 对应 `t_order`，别名 `u` 对应 `t_user`。
2. **二级缓存极速匹配**：组件拿着 `[用户ID + 页面编码 + 物理表名]` 碰撞 **Caffeine 本地缓存**。由于用户的权限配置在登录时就已经在 **Redis** 中合并预热好了，系统能以微秒级的速度捞出当前页面该表的 **JSON 行规则树**。
3. **沙箱 SpEL 表达式计算**：启动一个**彻底关闭了反射和系统调用权限的 `SimpleEvaluationContext` 只读安全沙箱**，去计算 JSON 规则树中带有占位符的属性值。例如，把规则里的动态组织架构函数，实时计算并翻译成一串具体的物理部门 ID（如将 `#user.deptId` 脑补为 `101,102`）。
4. **SQL 强行缝合**：将计算好的行过滤条件，结合第一步发现的真实别名（如改写为 `o.dept_id IN (101,102)`），通过 `AndExpression` 节点强行挂载到原 SQL 的 `WHERE` 分支树末尾。
5. **字段别名追踪映射（精髓）**：重写组件继续扫描 `SELECT` 的查询字段。如果 Vanna 产生了改名幻觉，写成了 `SELECT o.salary AS sly`，JSQLParser 会通过别名对照表，把 `o` 还原为 `t_order`。
   - 系统成功在运行时将大模型的乱起名，在语法树层面精确定位为了 **`t_order : salary`**。
   - 查阅本地缓存发现 `salary` 属于当前页面的列黑名单，于是，系统会动态将临时别名 `"sly"` 连同它在 `SELECT` 中的**绝对位置索引（Index）**一起打入当前请求的 `ThreadLocal` 禁用集合中。
6. **安全硬熔断**：如果大模型生成了带有语法错误的恶性 SQL，导致 JSQLParser 解析崩溃，系统会触发最高级别的硬熔断，直接中断报错，严防未加安全限制的语句发送到物理数据库。

第三步：数据库执行与结果集返回（数据执行层）

安全的物理 SQL 编译完成后发送给数据库执行。因为 AI 生成的列具有极大的不确定性，后端统一使用由键值对组成的动态列表——**`List<LinkedHashMap>`** 来接收返回的行数据（`LinkedHashMap` 完美保持了数据库返回的原始列顺序，以匹配位置索引）。此时，因为 Vanna 输出了 `AS sly`，所以结果集中的 `Key` 名字叫做 `"sly"`。

第四步：列权限内存级定向裁剪与洗白（视图层 AOP）

在数据准备转为 JSON 返回给前端之前的最后一关，列权限 AOP 切面组件被激活：

1. **快速失败（Quick-Fail）**：切面优先判断。如果当前页面的字段黑名单为空，或者当前用户是系统超级管理员，切面直接 `return;` 退出，后续的内存遍历完全不执行，损耗为零。
2. **内存双层迭代裁剪**：若存在限制，切面直接在内存中对 `List<LinkedHashMap>` 展开双层循环遍历（行迭代 + 列键值对碰撞）。
   - **针对完全禁止（DENY）的列**：当遇到 `"sly"` 时，直接命中 ThreadLocal 里的动态黑名单。切面直接在内存中执行 `map.remove("sly")`（让该键值对从当前行中彻底剔除）或者执行 `map.put("sly", null)`。
   - **针对需要脱敏（MASK）的列**：当遇到 `"phone"` 时，切面取出真实手机号，调用后端的脱敏工具类瞬间将其改写为打码后的静态安全文本（如 `"138****5678"`）重新 `put` 回 Map 中。
3. **零 GC 内存垃圾压力**：整个过程全部基于 JVM 堆内存的**纯指针移动和引用替换**，没有创建任何新的业务对象，对垃圾回收（GC）产生的压力几乎为零，完美避开了高并发场景下的 Full GC 停顿风险。 Jackson 序列化器此时只做原封不动的标准输出。

第五步：前端视觉隔离与全栈闭环

1. 用户成功登录系统时，后端随菜单树一起将 `denyColumns`（静态字段黑名单数组）下发并存储在前端状态管理器中。
2. 前端在拿到后端的 `List<Map>` 结果集时，需要通过遍历 Map 的 Key 来动态渲染表格的列。此时前端配合 `v-if="!permissionStore.denyColumns.includes(columnKey)"` 进行控制。
3. 由于后端提前在 Map 层面移除了该键或将其赋值为了 `null`，即便懂技术的用户通过 F12 恶意调出前端组件、或者直接通过 Postman 抓取接口 JSON 响应包，也只能拿到 `null` 或打码文本，实现了完美的视觉与安全数据双重隔离。

------

三、 高性能分布式两级缓存（Caffeine + Redis）架构

为了对抗 MyBatis-Plus 和动态 SQL 拦截器在每一次分页、count 统计、列表拉取时带来的高频元数据检索压力，本方案设计了完整的 **Caffeine（本地二级内存缓存）+ Redis（分布式一级缓存）** 的高并发架构：

1. **静态存储减肥**：管理员在后台配置、以及后端在两级缓存中存储的，永远是稳定的、标准的 **`[物理表名 -> 字段黑名单列表]`** 和 **`[物理表名 -> 结构化 JSON 行规则树]`**。不需要夹杂任何大模型的动态别名和随机成分，让缓存架构极度减肥。
2. **Caffeine 软引用防爆**：本地内存缓存设置合理的容量与最大限制（如允许缓存 2W 条规则快照），强写 10 分钟后强制过期失效。同时，**启用软引用（Soft Values）策略**，在 JVM 内存吃紧时允许 GC 自动强制回收内存，绝对拒绝 OOM。
3. **防击穿高阻断**：如果 Redis 发生意外未命中，核心插件**禁止直接查询原始数据库关系大表**，而是直接触发最高安全级别阻断方案（默认生成 `AND 1=0` 过滤条件），确保核心生产库绝对不会发生缓存击穿后的 SQL 洪水灾难。
4. **最终一致性强清广播**：当管理员在后台修改了角色的行列权限，后端更新数据库，并立刻 `del` 掉 Redis 中受影响用户的 Hash 键。随后借助 Redis 优秀的 **Pub/Sub (发布订阅)** 机制，向全局通道广播一条强清消息。集群中所有运行的服务器实例其后台监听类瞬间被唤醒，同步执行本地 Caffeine 的单键或批量擦除，完成双级缓存的平滑无感重建。

------

四、 核心总结

这套方案之所以被称为“中量级”，是因为它在工程落地上进行了一次极其聪明的降级：**把复杂的业务权限逻辑留在了 Java 开发者最擅长的业务层（AOP），把行权限的底层技术缩减到了一个不写 SQL 的安全沙箱中，把大模型天马行空的起名幻觉通过 JSQLParser 运行时树状剥离，最后把底层的转换框架（Jackson）解放出来做纯粹的本职工作**。整套方案对核心逻辑没有丝毫妥协，但在工程落地的难度、稳定性和运行性能上，都达到了工业级的顶级强度。
