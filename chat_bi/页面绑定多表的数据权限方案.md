# 页面绑定多表的数据权限方案

## 一、需求背景与核心挑战

在原有"页面-单表"权限模型下，一个菜单页面仅对应一个业务实体。但实际业务中，**一个功能页面往往同时涉及多张数据表**：

- **订单审核页**：主表 `Order` + 明细表 `OrderItem` + 操作日志 `OrderLog`
- **客户详情页**：主表 `Customer` + 联系人 `Contact` + 跟进记录 `FollowUp`
- **财务报表页**：汇总表 `FinanceSummary` + 明细表 `FinanceDetail` + 凭证表 `Voucher`

核心挑战在于：**同一个页面上下文（MenuCode）下，不同数据表需要各自独立的行权限与列权限策略**，且运行时需精准识别"当前 SQL 正在操作哪张表"，避免权限串位或漏控。

---

## 二、数据模型层：无需改表，复用现有枢纽表

现有 `app_role_menu_data_scope` 表的联合业务维度为：

```
[role_id + menu_code + entity_name] → [row_rule_id + col_rule_id]
```

**该设计天然支持"一对多"绑定**。同一 `menu_code` 下可存在多条记录，每条对应不同 `entity_name`，分别指向独立的行/列规则。

**示例配置态：**

| 角色 | 页面编码 | 业务实体 | 行规则 | 列规则 |
|------|---------|---------|--------|--------|
| 区域经理 | `order:audit:index` | `Order` | 本区域及下级部门 | 成本字段脱敏 |
| 区域经理 | `order:audit:index` | `OrderItem` | 跟随主表范围 | 采购价不可见 |
| 区域经理 | `order:audit:index` | `OrderLog` | 仅本人操作记录 | 无限制 |

## 三、配置管理层：从"单表单规则"升级为"页面级规则矩阵"

### 3.1 配置界面形态

后台权限配置页面需从原来的"一对一"表单，改造为**"页面维度下的规则矩阵"**：

```
┌─────────────────────────────────────────────────────────┐
│  页面：order:audit:index（订单审核页）                      │
├─────────────┬─────────────┬─────────────┬───────────────┤
│  数据实体    │  行权限规则  │  列权限规则  │   操作        │
├─────────────┼─────────────┼─────────────┼───────────────┤
│  Order      │  规则A       │  规则X      │  编辑 / 删除   │
│  OrderItem  │  规则B       │  规则Y      │  编辑 / 删除   │
│  OrderLog   │  规则C       │  —          │  编辑 / 删除   │
│  + 新增实体  │             │             │               │
└─────────────┴─────────────┴─────────────┴───────────────┘
```

### 3.2 默认规则继承机制

为避免每张表都逐一手动配置的繁琐，引入**两级继承策略**：

| 层级 | 说明 |
|------|------|
| **页面默认规则** | 在页面级别预设一套"默认行规则"和"默认列规则"。页面下新绑定的表如未单独配置，自动继承默认规则。 |
| **规则模板库** | 将高频规则（如"本部门及下级"、"仅本人数据"、"全量只读"）抽象为可复用模板，一键应用到多个实体。 |

### 3.3 规则冲突消解（多角色叠加时）

当用户拥有多个角色，且不同角色对**同一页面下的同一张表**配置了不同规则时：

- **行权限**：取**并集**（OR 关系），确保不丢失任何角色有权查看的数据。
- **列权限**：取**最严格策略**，优先级为 `DENY（不可见）> MASK（脱敏）> ALLOW（正常）`。

该消解逻辑在**用户登录阶段的权限快照预热**时一次性计算完成，运行时直接消费计算结果，避免实时运算的性能损耗。

## 四、运行时匹配层：拦截器精准识别"当前操作表"

### 4.1 匹配维度升级

运行时，MyBatis-Plus 拦截器需从"二维匹配"升级为**"三维精准匹配"**：

```
匹配键 = 当前用户ID + 当前页面编码(MenuCode) + 当前物理表名
```

拦截器在执行查询时，内部已能识别当前 SQL 涉及的物理表（如 `t_order`、`t_order_item`）。结合 ThreadLocal 中的 `MenuCode`，即可从缓存中捞出**该页面下该表专属**的权限规则。

### 4.2 未配置场景的降级策略

若某页面下某张表**未配置任何规则**（包括未继承默认规则），拦截器执行**最高安全级别阻断**：

- 直接生成恒假条件（如 `AND 1=0`），使该表数据返回空结果集。
- 杜绝"未配置即放行"的安全漏洞。

### 4.3 多表 Join 时的别名防歧义

当页面查询涉及多表 Join 且存在重名字段（如多个表都有 `id`、`dept_id`）时：

- 拦截器在拼接权限条件时，必须**强制附加当前表的专属别名前缀**（如 `o.dept_id IN (...)` 而非裸写 `dept_id IN (...)`）。
- 该别名由 MyBatis-Plus 内部解析当前 SQL 时动态获取，确保不因列歧义导致 SQL 执行崩溃。

## 五、列权限层：前端菜单树与 AOP 反射的联动改造

### 5.1 菜单树权限快照结构升级

用户登录时返回的菜单树中，每个菜单节点的列权限信息需从"一维数组"升级为**"实体映射结构"**：

```
改造前：
  menu.denyColumns = ["costPrice", "supplierPhone"]

改造后：
  menu.entityColumnRules = {
    "Order":      ["profit", "channelCost"],
    "OrderItem":  ["purchasePrice", "supplierName"],
    "OrderLog":   []
  }
```

### 5.2 前端视觉隔离

前端通用表格/详情组件在渲染时：

1. 根据当前数据接口对应的业务实体名（如 `OrderItem`），从菜单节点中读取对应的 `denyColumns` 数组。
2. 对命中黑名单的列，通过 `v-if` 级别控制**整列不渲染**，实现视觉隔离。
3. 对命中脱敏名单的列，前端可预先显示占位符（如 `****`），但**真实脱敏逻辑仍由后端 AOP 执行**，防止抓包绕过。

### 5.3 后端 AOP 反射清洗

AOP 切面在方法返回前执行字段清洗时：

1. 根据返回的 DTO/VO 类型，反查其对应的业务实体名。
2. 从缓存中抓取该实体在当前页面下的列黑名单。
3. 对 `DENY` 字段反射置 `null`；对 `MASK` 字段调用脱敏引擎改写。
4. 若一个页面返回多个实体的混合结果集（如主从对象嵌套），切面需**递归扫描嵌套对象**，逐层匹配对应实体的列规则。

## 六、主从表联动场景：子表权限是否跟随主表

### 6.1 独立过滤模式（推荐默认）

页面下各表拥有完全独立的行权限规则。适用于：
- 订单列表按部门过滤，但订单日志按操作人过滤。
- 各子表数据敏感度不同，需差异化管控。

### 6.2 跟随主表模式（业务级联动）

适用于"看到哪些主表记录，就只能看到这些记录下的子表数据"的强关联场景。实现方式：

- 在子表的行规则 JSON 中，通过 SpEL 自定义函数引用主表权限结果。
- 或配置子表规则为：`主表外键 IN (当前用户可见的主表 ID 集合)`。
- 该集合由登录预热阶段预计算并缓存，避免运行时重复查询。

---

## 七、缓存架构适配：键设计与预热逻辑微调

### 7.1 本地缓存键（Caffeine）

保持原有复合键设计，天然兼容：

```
Key = {userId}:{menuCode}:{tableName}
```

### 7.2 Redis 全量权限快照结构

用户登录时预热的权限快照，Redis 存储结构从"页面级单规则"调整为"页面内多实体规则包"：

```
Hash Key: permission:snapshot:{userId}
Hash Field: {menuCode}
Hash Value: {
    "Order": { "rowRule": {...}, "colRule": {...} },
    "OrderItem": { "rowRule": {...}, "colRule": {...} },
    "OrderLog": { "rowRule": {...}, "colRule": null }
}
```

### 7.3 缓存击穿防护

若 Redis 中某 `menuCode` 下缺少某 `entityName` 的规则记录（极端缓存丢失场景）：

- 本地 Caffeine 未命中 → Redis 未命中 → **禁止回查数据库**。
- 直接降级为 `AND 1=0` 阻断，确保生产库不受缓存击穿后的查询洪水冲击。

### 7.4 缓存一致性广播

当管理员调整某角色的页面权限时：

1. 更新数据库。
2. 根据受影响的角色，找出所有在线用户，删除其 Redis 中的权限快照键。
3. 通过 Redis Pub/Sub 广播清空各节点的本地 Caffeine 缓存。
4. 受影响用户下次请求时，自动触发重新加载与预热。

## 八、边界条件与特殊场景

| 场景 | 处理策略 |
|------|----------|
| **同一张表在同一个页面被多次 Join** | 拦截器按表别名区分（如 `o` 和 `o2`），分别挂载权限条件。 |
| **页面新增业务表但未配置权限** | 走页面默认规则；无默认规则则阻断（`1=0`）。 |
| **导出 Excel 跨多表** | 导出接口必须携带 `X-Menu-Code`，逐张表经过相同的拦截器与 AOP 清洗流程。 |
| **写操作（Update/Insert）** | 默认不拦截。若需控制，在 Service 层显式校验数据归属，或单独配置写权限规则。 |
| **聚合查询（COUNT/SUM）** | 聚合函数同样经过拦截器，WHERE 条件自动拼接，确保统计结果也受权限约束。 |

## 九、实施路径建议

| 阶段 | 工作内容 | 产出 |
|------|---------|------|
| **第一阶段：模型确认** | 确认无需改动数据库表结构，梳理现有页面涉及的多表清单。 | 多表绑定关系清单 |
| **第二阶段：配置层改造** | 后台权限管理界面升级为"页面-规则矩阵"，支持默认规则继承与模板复用。 | 新版配置 UI |
| **第三阶段：运行时适配** | 调整 MP 拦截器的匹配逻辑，确保按 `tableName` 精准捞取规则；完善未配置场景的降级阻断。 | 运行时权限引擎 |
| **第四阶段：列权限联动** | 改造前端菜单树结构、通用表格组件；调整后端 AOP 切面支持嵌套对象递归扫描。 | 前后端列权限闭环 |
| **第五阶段：缓存与性能** | 调整 Redis 快照结构，验证 Caffeine 复合键命中逻辑，压测多表 Join 场景下的性能损耗。 | 性能基线报告 |
| **第六阶段：灰度与回归** | 选取一个典型多表页面灰度上线，验证主从表联动、导出、缓存一致性等边界场景。 | 上线验收报告 |

## 十、总结

本方案的核心设计原则是：**底层数据模型零改动，通过升级配置形态、运行时匹配维度、列权限快照结构，天然支持"一个页面绑定多个表"的复杂场景**。

原有五表联动架构、Caffeine+Redis 两级缓存、SpEL 安全沙箱、AOP 反射清洗等核心机制均完整复用，仅需在**配置层交互**、**缓存 Value 结构**、**前端菜单树协议**三个层面进行适应性升级，即可实现多表精细化权限管控。
