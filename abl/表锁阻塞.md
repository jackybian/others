# SQL Server 读写阻塞问题分析与解决方案

## 问题背景

ERP 系统正在频繁地往 `T_ODRF2` 表中写入、修改单据（通常带有排他锁 `X-Lock`），而我们的同步查询需要获取共享锁（`S-Lock`）才能读取数据。

由于 SQL Server 的默认事务隔离级别为 **"已提交读（Read Committed）"**，读取操作在访问被写事务锁定的数据行时，会被写事务阻塞，直到写事务提交或读取超时。

---

## 问题现象

- 同步抽取查询长期被 ERP 写入事务阻塞
- 查询连接最终因超时而断开
- 数据同步延迟增大，影响下游业务

---

## 解决方案对比

### 方案一：使用 `WITH (NOLOCK)` 提示

```sql
SELECT * FROM T_ODRF2 WITH (NOLOCK) WHERE ...
```

**优点：**

- 实现简单，无需数据库层面改动
- 查询不会被写事务阻塞

**缺点：**

- 可能读取到未提交的脏数据（dirty read）
- 数据一致性无法保证，不适合对准确性要求高的同步场景

------

### 方案二：开启读已提交快照隔离级别（RCSI）

sql

```
ALTER DATABASE [数据库名] SET READ_COMMITTED_SNAPSHOT ON;
```



**原理：**

开启 RCSI 后，SQL Server 会利用 `tempdb` 维护数据行的历史版本（行版本控制）。当一个写事务正在修改某行数据且尚未提交时，查询请求不会被阻塞，也不会读到未提交的脏数据，而是从 `tempdb` 中获取该行数据**修改之前**的已提交快照版本。

**优点：**

- 读取不会被写入阻塞，彻底解决阻塞问题
- 读取到的数据是事务一致性的已提交版本，无脏读
- 无需修改应用代码或查询语句

**代价：**

| 影响项            | 说明                                                         |
| :---------------- | :----------------------------------------------------------- |
| `tempdb` 压力增加 | 需要存储修改前的行版本，增加 `tempdb` 空间占用和 I/O 负载    |
| 写性能轻微下降    | 每行数据额外增加 14 字节版本指针，写入性能通常下降 2%~5%，对大多数 ERP 系统影响可忽略 |

------

## 推荐方案

建议优先采用 **RCSI（方案二）**，理由如下：

- 彻底消除读写阻塞，同时保证数据一致性
- 无需修改现有查询或业务代码
- 性能代价在可接受范围内，适合生产环境

------

## 实施注意事项

1. 开启 RCSI 前需确认 `tempdb` 有足够的磁盘空间和 I/O 能力
2. 该操作会清空该数据库上的所有活动事务，建议在维护窗口执行
3. 开启后可通过以下 SQL 确认状态：

sql

```
SELECT name, is_read_committed_snapshot_on 
FROM sys.databases 
WHERE name = '你的数据库名';
```



------

## 结论

在数据一致性要求高、读写冲突明显的场景下，RCSI 是比 `NOLOCK` 更优的解决方案，能够在**不牺牲一致性的前提下**彻底解决阻塞问题。
