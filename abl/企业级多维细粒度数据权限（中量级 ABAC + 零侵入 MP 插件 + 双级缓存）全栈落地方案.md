**企业级多维细粒度数据权限（中量级 ABAC + 零侵入 MP 插件 + 双级缓存）全栈落地方案**

本方案采用 **ABAC（基于属性的访问控制）** 混合模型构建。核心目标是解决企业级 Web 项目中“**同一用户在不同页面、针对同一实体，看到的数据范围（行权限）与可见字段（列权限）各不相同**”的硬核安全痛点。

方案摒弃了传统的“JSQLParser 盲目改写 SQL”与“底层序列化重写”等重量级高危做法，采用**面向对象注入**与**安全沙箱 SpEL 驱动**的“中量级”改良架构，在保证“零底层框架侵入”的同时，利用**内存级高性能双级缓存**对抗高频 SQL 拼接带来的网络与 CPU 开销。

一、 系统核心模型与五表联动设计

通过 3 张基础维度主表和 2 张权限规则映射表，建立起“人（角色）、面（页面）、品（实体）、规（行列规则）”的多维立体动态矩阵。

```
【维度主表】                                     【权限控制纽带表】
+----------------+                              +-------------------------------+

|  sys_role      | ---(角色维度: 一对多)---------> | sys_role_menu_data_scope     |
+----------------+                              +-------------------------------+

                                                | - role_id      (谁)           |
+----------------+                              | - menu_code    (哪个页面)      |

|  sys_menu      | ---(页面维度: 一对多)---------> | - entity_name  (什么业务对象)   |
+----------------+                              | - row_rule_id  (纵向看多少行)   |

                                                | - col_rule_id  (横向看多少列)   |
+----------------+                              +-------------------------------+

|  sys_entity    | ---(实体维度: 一对多)-----------/               |               |
+----------------+                                              |               |
                                                      (关联行规则) /             \ (关联列规则)
                                                                  v               v
                                                +----------------+  +-------------------+

                                                | sys_data_rule  |  | sys_column_rule   |
                                                +----------------+  +-------------------+

                                                | json_rules_tree|  | json_rules_config |
                                                +----------------+  +-------------------+
```

1. 维度主表设计

- **系统角色表 (`sys_role`)**：定义组织架构中的安全载体（角色主键、角色唯一编码 `role_code`、角色名称）。
- **系统菜单页面表 (`sys_menu`)**：定义前端页面的唯一入口（菜单主键、**菜单唯一编码 `menu_code`**，如 `order:audit:index`）。
- **业务实体表 (`sys_entity`)**：定义系统受控的数据对象（实体主键、实体英文字符名 `Order`、对应的数据库物理主表名 `t_order`）。
- 多维复合关联表 (`sys_role_menu_data_scope`)

**整个方案的核心交叉枢纽**。系统在运行时通过 `[当前用户角色集 + 当前请求页面编码 + 正在查询的业务实体]` 这一复合维度，来唯一确定一条权限过滤策略。

- **核心字段**：主键、角色ID、菜单编码 (`menu_code`)、业务实体名、关联的行规则ID (`row_rule_id`)、关联的列规则ID (`col_rule_id`)。
- 数据权限行规则表 (`sys_data_rule`)

为了兼顾“结构化易配置”与“应对复杂多变业务的弹性伸缩能力”，行规则采用 **JSON 树作为结构化外壳，并在具体的 `value` 节点中嵌入微量的、受控的 SpEL 变量或自定义函数。**

- **核心字段**：规则主键、规则名称、业务实体名、**动态规则配置 (`json_rules_tree`)**。
- **配置标准规范**：
  - 通过外层 JSON 定义逻辑关系（如 `AND` / `OR`）以及操作符（如 `IN`、`EQ`、`LIKE`）。
  - 在数值（Value）节点中嵌入 SpEL 占位符。例如：使用 `#user.id` 动态提取当前用户的实时属性；使用 `@deptService.getChildIds(#user.deptId)` 实时触发组织架构树向下递归计算。
  - **业务收益**：彻底告别死锁的 5-6 种固定部门策略，支持跨地区兼职、动态项目组、按产品线交叉隔离等变态场景。
- 列权限规则配置表 (`sys_column_rule`)

定义横向切块的字段可见性及脱敏行为。

- **核心字段**：列规则主键、规则名称、业务实体名、**字段控制清单 (`json_rules_config`)**。
- **控制清单存储结构**：
  - 存储为结构化 JSON 数组，明确指定某个列名及其对应的控制策略。
  - `DENY`（完全不可见）：Java AOP 层利用反射直接抹除该属性值为 `null`，前端配合 `v-if` 实现整列销毁的视觉隔离。
  - `MASK`（部分可见）：Java AOP 层通过脱敏引擎将字符串处理为带星号的脱敏安全文本（如 `138****8888`），防止抓包。

二、 后端全链路架构与技术实现思路

方案采用**“前端显式传递页面上下文 + 后端两级缓存护航 + MyBatis-Plus 官方拦截器无感注入”**的架构设计，确保 100% 契合现代面向对象的开发生态。

```
[前端请求] ──> (Header 带上 X-Menu-Code: order:audit) ──> [Spring MVC 拦截器]
                                                                  │ (存入 ThreadLocal)
                                                                  ▼
[执行 MP 查询方法] ──> 例如执行: orderMapper.selectList(wrapper);
        │
        ▼ (MyBatis-Plus 官方拦截器自动运行)
[DataPermissionInterceptor 拦截器]
   - 读取 ThreadLocal 中的 MenuCode，读取用户属性
   - 面向「Caffeine + Redis 二级缓存」捞出当前页面该表的「JSON规则树」
   - 启动「SimpleEvaluationContext 安全沙箱」解析其中的 SpEL 变量/函数值
   - 自动在 MP 生成的 SQL 后面无感拼接 WHERE 权限碎片条件
        │
        ▼
[数据库执行] ──> [获得结果集]
        │
        ▼ (Controller 返回前)
[AOP 列权限切面] ──> 扫描 @SensitiveField 注解 ──> 反射抹除/打码黑名单字段 ──> [前端接收安全 JSON]
```

1. 页面上下文传递与安全校验 (HTTP 链路层)

- **前端上报上下文**：前端（如 Axios 统一请求拦截器）在发起任何数据请求时，自动从当前 Vue-Router 路由节点动态获取菜单编码，并将其作为自定义请求头（如 `X-Menu-Code: order:audit`）发送给后端。
- **上下文生命周期控制**：后端编写一个 `Spring HandlerInterceptor`（MVC 拦截器），统一拦截所有 HTTP 请求，提取 `X-Menu-Code`，并将其存入异步安全的 `ThreadLocal` 上下文中。请求结束时，在 `afterCompletion` 阶段强制清理，防止在高并发线程池复用场景下发生线程间数据污染。
- **路由防篡改与越权校验**：由于前端请求头是可伪造的，拦截器在捕获 `X-Menu-Code` 时，需在内存/Redis中比对 `【当前用户拥有的角色权限集】 -> 【该请求头的 MenuCode】 -> 【当前请求的 Controller 接口路由】` 三者是否具备合法的绑定关系。若不合法，认定为越权探测，直接返回 `403 Forbidden` 阻断请求。
- 行权限落地：MyBatis-Plus 内置 `DataPermissionInterceptor` 方案

开发人员完全保留 MyBatis-Plus 的面向对象开发规范（不写 SQL、不写 XML），由 MP 官方插件在底层完成安全的无感注入。

- **拦截注入机制**：在 MyBatis-Plus 拦截器链中，统一注册官方自带的 `DataPermissionInterceptor`，并自定义实现其 `MultiDataPermissionHandler` 接口。
- **运行时逻辑重写**：当执行任何单表或多表 Join 查询时，插件会自动将当前被扫描到的受控物理表名（如 `t_order`）和原有的 WHERE 条件传入该处理器。
- **条件缝合算法**：处理器结合当前页面上下文与用户标识，去双级缓存中匹配行权限 JSON 规则树。调用沙箱 SpEL 解析器，计算出 JSON 树中占位符的真实物理值（如将 `#user.id` 编译为 `1001`）。随后，将这些结构化条件直接转化为 JSQLParser 的 `Expression` 表达式节点，通过 `AndExpression` 强行挂载到 MP 生成的物理 SQL 末尾。
- SpEL 安全边界保障：`SimpleEvaluationContext` 沙箱机制

直接使用标准的 SpEL 表达式引擎允许执行任意 Java 反射和系统底层命令，存在严重的远程代码执行（RCE）漏洞。为了确保绝对的安全，必须在解析工具类中强制收紧执行沙箱：

- **隔离策略**：全面禁用标准的 `StandardEvaluationContext`。强行改用 **`SimpleEvaluationContext.forReadOnlyDataBinding()`**（开启只读数据绑定沙箱）。
- **权限最小化**：该沙箱全面禁用方法调用与构造函数，仅允许通过白名单机制显式将系统中安全的、专用于权限计算的 Service（如 `deptService`）作为函数解析器注入。黑客即便篡改了权限字符串，也绝对无法穿透沙箱，从源头上封杀 RCE 漏洞。
- 列权限落地：AOP 注解拦截与动态反射扫描

- **业务层清洗**：放弃改写 Jackson 底层序列化器的黑盒做法。在需要受控的返回对象（DTO/VO）属性上打上自定义注解（如 `@SensitiveField`）。
- **一键动态扫描**：编写通用的 AOP 切面类，仅拦截标记了特定脱敏注解的 Service 业务方法。在方法返回结果集给 Controller 之前，切面从缓存中抓取当前页面对应的列黑名单。整个 HTTP 请求的生命周期内，切面在方法返回时**集中执行一次且仅一次**对象属性遍历。
- **替换策略**：命中完全禁用黑名单（`DENY`）的属性直接利用反射将其值抹平为 `null`；命中脱敏黑名单（`MASK`）的调用脱敏引擎将其改写为静态星号文本（如 `138****8888`）。由于底层 Jackson 此时只处理标准的静态文本转换，系统的吞吐量和稳定性大幅提升，且极其容易打断点排查 Bug。

三、 高性能分布式两级缓存（Caffeine + Redis）架构

由于数据权限系统处于系统的最底层，MyBatis-Plus 拦截器在每一次单表查询、分页 count 统计、级联拉取时都会频繁触碰权限元数据。本方案设计了完整的 **Caffeine（本地二级内存缓存）+ Redis（分布式一级缓存）** 的高并发架构，确保整个权限框架的损耗降到微秒级。

```
                       [MyBatis-Plus 拦截器 / AOP 切面]
                                      │
                                      ▼
               +---------------------------------------------+

               |        Caffeine 本地缓存 (L2 Cache)          | ──(物理命中)──> [直接返回]
               +---------------------------------------------+
                                      │
                                    (未命中)
                                      ▼
               +---------------------------------------------+

               |         Redis 分布式缓存 (L1 Cache)          | ──(命中)──> [写入本地内存] ──> [返回]
               +---------------------------------------------+
                                      │
                                    (未命中)
                                      ▼
               +---------------------------------------------+

               |            DB 数据库安全防击穿降级            | ──> [回写 Redis] ──> [返回]
               +---------------------------------------------+
```

1. 登录阶段的“全量权限快照预热”

为了实现运行时的“零库表查询”，系统在用户登录成功、签发 Token 的黄金阶段，将该用户所拥有的**所有角色**在系统中的多维权限配置进行**一次性合并计算**。

- **冲突重组**：对相同的 `[menu_code + entity_name]` 进行权限交集或并集运算。如果多个角色规则冲突，行权限取最大并集数据范围，列权限取最严格的黑名单。
- **持久化至 Redis**：将该用户最终计算出的全量“页面权限快照树”存入 Redis 缓存（采用 Hash 结构存储），并设置与用户 Token 完全一致的过期时间（TTL）。
- 运行阶段的 Caffeine 内存穿透缓冲

当请求到达后端，进入 MyBatis-Plus 插件和 AOP 切面时，系统首先检索部署在当前应用进程内存中的 **Caffeine 本地缓存**。

- **本地缓存键设计**：采用由 `userId + menuCode + tableName` 组成的复合唯一物理键。
- **内存溢出与防爆配置**：本地缓存设置合理的初始容量与最大限制（如允许缓存 2W 条规则快照），强写 10 分钟后强制过期失效。同时，**启用软引用（Soft Values）策略**，在 JVM 内存吃紧时允许 GC 自动强制回收内存，拒绝 OOM。
- **查询命中逻辑**：
  1. 检查 Caffeine 内存。若命中，直接返回 JSON 规则树并交给沙箱 SpEL 解析执行。
  2. 若 Caffeine 未命中，发起一次 Redis 的 `hget` 操作。若 Redis 命中，将结果反序列化并同步**回写**到当前进程的 Caffeine 内存中。
- **安全防击穿降级**：如果 Redis 发生意外未命中（如极端情况缓存丢失），核心插件**禁止直接查询原始数据库关系大表**，而是直接触发**最高安全级别阻断方案**（默认生成 `AND 1=0` 过滤条件），确保核心生产库绝对不会发生缓存击穿后的 SQL 洪水灾难。
- 运营管理阶段的“双级缓存主动分布式强清机制 (Consistency)”

当权限管理员在后台修改了某个角色的权限数据、或者用户在组织架构中调离了部门，缓存必须在集群环境下保持**最终一致性**，必须引入 **Redis Pub/Sub（发布订阅）** 进行跨节点的主动通知。

- **数据流切断**：管理员在后台点击“保存权限”时，后端先更新数据库，随后执行清除命令：根据受影响的角色，找出关联的所有在线 `userId`，强行从 Redis 中 `del` 掉对应的键。
- **集群消息广播**：依靠 Redis 自身的通道（如 `convertAndSend`），向整个微服务/多实例集群发送一条清空本地内存的轻量级广播。
- **本地瞬时擦除**：所有订阅了该通道的服务器实例，其后台监听类瞬间被唤醒，执行本地 Caffeine 的单键或批量擦除。当下一次受影响的用户在前端点击页面发起请求时，系统自动触发重新加载计算流，完成双级缓存的无感平滑重建。

四、 前端动态感知与视觉隔离闭环

真正高体验的权限系统需要前后端高度解耦而又紧密联动，避免页面出现大面积空白。

1. **菜单树附带权限快照**：用户成功登录系统时，后端返回的路由菜单树中，每个菜单节点都应附带该角色在该页面的 `denyColumns`（字段黑名单数组）。
2. **动态列隐藏（视觉隔离）**：前端统一封装通用表格渲染组件（如 Vue 3 + Element Plus 的表格）。组件在加载时，自动读取当前路由节点下的 `denyColumns` 数组。如果发现表格中的某列 `prop` 存在于黑名单中，整个 `<el-table-column>` 节点将**直接不被渲染（v-if 级别控制）**。
3. **双重防线保障**：由于前端 `v-if` 隐藏了整列，配合后端 AOP 提前将该字段清洗为 `null` 的机制，即便懂技术的用户通过 F12 恶意调出前端组件、或者直接通过 Postman 抓取接口 JSON 响应包，也只能拿到 `null` 或打码文本，实现了完美的视觉与数据双重隔离。

五、 极端边界条件与性能损耗控制

1. **复杂联查 (Join) 且存在重名列的歧义处理**：
   - *问题*：当多表 Join 时，如果多个表存在相同字段（如 `id` 或 `dept_id`），若直接拼接过滤条件会导致数据库抛出 `Column in where clause is ambiguous`（列歧义）错误。
   - *对策*：MyBatis-Plus 处理器在运行时，会精确获取 MP 当前生成的表别名（如将物理表 `t_order` 映射为别名 `o`）。在沙箱解析 SpEL 表达式拼接字符串时，强制加上该表的专属别名前缀（如改写为 `o.dept_id IN (...)`），从根本上避免列歧义崩溃。
2. **写操作 (Insert/Update) 的权限隔离**：
   - *原则*：本方案的核心拦截器默认**仅对 Select 查询语句进行动态 WHERE 追加**。
   - *对策*：对于写操作（如更新、修改），企业中通常通过在 Service 层引入常规的方法级行鉴权（如校验数据归属人），或者利用 MyBatis-Plus 的 `UpdateWrapper` 配合 AOP 显式注入隔离条件，避免写操作被全局无感拦截器误伤。
3. **批量导出 (Excel) 的权限联动**：
   - *机制*：当用户点击页面上的“导出 Excel”按钮时，其触发的下载接口必须传入与列表查询完全一致的 `X-Menu-Code` 请求头。后端导出服务必须经过相同的 `DataPermissionInterceptor` 与 AOP 反射脱敏流，确保导出的物理文件同样实现了行列裁剪，防止敏感数据资产大批量外泄。
