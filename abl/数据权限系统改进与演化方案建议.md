# 数据权限系统改进与演化方案建议
## 1. 架构体系演进：从“耦合”到“解耦”
目前行权限与字段权限在 sys_data_permission 表中高度耦合，建议演进为 “规则-策略-授权” 三层架构。

- 规则解耦 ：
  - 行过滤规则库 ( sys_data_row_rule ) ：独立定义 SQL 模板（如 dept_id = ${deptId} ），支持多角色复用，消除 SQL 冗余。
  - 字段脱敏包 ( sys_data_field_rule ) ：独立定义 field_configs (JSONB)，将常用的脱敏组合（如：基础敏感信息脱敏包）打包管理。
- 授权中心化 ( sys_data_permission ) ：
  - 作为关联表，仅存储 Target(谁) + Resource(资源) + RowRule(行规则) + FieldRule(列规则) 的映射关系。
  - 核心逻辑 ：授权记录的存在即代表“准入”，具体的行过滤和列脱敏通过关联的规则 ID 动态加载。
## 2. 安全策略优化：默认禁止（Deny by Default）
为了符合现代安全审计要求，权限判定逻辑应遵循“最小权限原则”。

- 行级权限控制 ：
  - 无授权即禁止 ：如果用户对某张表（非系统表）没有任何权限记录，SDK 自动注入 1=0 条件。
  - 字段权限隐含准入 ：如果用户仅配置了字段权限而未写行 SQL，系统应识别为“已授权但无行级约束”，此时行级应自动放行（返回 null ），而非拦截。
- 字段权限控制 ：
  - 默认放行 ：为了保证业务可用性，未明确配置脱敏策略的字段默认允许查看。
  - 精确脱敏 ：仅对 field_configs 中声明为 MASK 、 HIDE 、 DENY 的字段执行脱敏逻辑。
## 3. 多规则合并策略（Conflict Resolution）
当一个角色或用户拥有多条数据权限规则时，系统需执行以下合并算法：

- 行权限合并（Additive） ：采用 并集 (OR) 策略。只要有一条规则允许访问该行，用户即可见。
- 字段权限合并（Most Permissive） ：采用 最高等级覆盖 策略。
  - 定义等级： ALLOW (4) > MASK (3) > HIDE (2) > DENY (1) 。
  - 当多条规则冲突时，取最高等级。例如：规则 A 要求脱敏，规则 B 允许放行，则最终结果为“放行”。
## 4. PostgreSQL 深度兼容性
针对 PostgreSQL 特性，需持续加固以下技术点：

- JSONB 类型安全 ：确保所有涉及 field_configs 的操作均通过 JacksonTypeHandler ，且 JDBC URL 包含 stringtype=unspecified 。
- 模糊查询规范 ：严禁使用 CONCAT ，统一使用 || 连接符（如 LIKE '%' || #{param} || '%' ），防止类型推断失败。
- 双 Key 匹配机制 ：在注入权限缓存/JWT 时，同时生成“业务名称（entity_name）”和“技术表名（entity_table）”的 Key，解决数据库配置与 Java 类名不一致导致的匹配失效。
## 5. 系统健壮性与性能
- 缓存失效策略 ：
  - 负缓存 (Negative Caching) ：缓存空规则（ [] ）以保护数据库，过期时间 1 小时。
  - 联动清理 ：在权限 Save/Update/Delete 时，必须通过 Redis 模式匹配（ keys + delete ）精准清理对应表的所有用户缓存。
- 依赖解耦 ：
  - 在 Spring Security 配置类与策略工厂中使用 @Lazy 延迟注入 Service，防止因 MyBatis 代理对象未就绪导致的容器启动循环依赖。
- 元数据补偿 ：
  - Server 端在处理权限规则时，若发现冗余字段缺失，应自动根据 resource_id 从 sys_data_resource 表补偿 entity_table 信息。
## 6. 未来 Roadmap 建议
- 权限模拟器 ：在管理后台提供“权限审计”功能，输入用户 ID 即可实时预览其合并后的 SQL 片段和字段脱敏清单。
- 字段脱敏算法注册表 ：建立标准的 MaskStrategyRegistry ，支持通过简单的规则配置（如 maskRule: PHONE ）调用不同的脱敏算法。
