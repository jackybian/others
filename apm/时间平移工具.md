## 时间平移工具

### 5.1 脚本位置

```
scripts/time_shift_tool.py
```

### 5.2 功能概述

以需求的"开始时间"为基准，将整条业务链路上所有时间字段统一平移 N 天。

**核心特性**：

- **两阶段执行**：先导出快照，人工确认后再执行更新
- **事务控制**：出错自动回滚，保证数据一致性
- **审计日志**：记录每条记录的修改前后值，便于追溯
- **全链路覆盖**：需求 → 立项 → 开发计划 → 任务 → 交付 → 文档

### 5.3 关系链

```
需求 (无子表)
  │
  ▼
立项 (无子表)
  │
  ▼
开发计划 ──→ 子表: apm_project_develop_plan_task ──→ 任务 (无子表)
                                                      │
                                                      ▼
                                                    交付 ──→ 子表: apm_project_task_delivery_list ──→ 文档 ──→ 子表: apm_doc_file
```

### 5.6 详细执行流程

#### 阶段一：数据快照导出

**函数**: `export_original_data(requirement_doc_id)`

**执行步骤**：

1. 根据 `requirement_doc_id` 查询需求表
2. 通过 `requirement_doc_id` 关联查询立项表
3. 通过 `initiation` 字段关联查询开发计划表
4. 通过 `develop_plan_doc_id` 关联查询任务表
5. 通过 `task_doc_id` 关联查询交付表
6. 通过 `master_doc_id` 查询交付列表，获取 `file_doc_id`
7. 通过 `file_doc_id` 查询文档表

**输出文件**: `time_snapshot_before.json`

**快照数据结构示例**：

```
{
  "metadata": {
    "root_requirement_doc_id": "req_001",
    "export_time": "2024-01-10 10:30:00"
  },
  "records": [
    {
      "table": "apm_project_requirement",
      "data": {
        "id": 1,
        "doc_id": "req_001",
        "request_time": "2024-01-01 00:00:00",
        "approve_time": "2024-01-02 00:00:00",
        "start_time": "2024-01-01 00:00:00",
        "end_time": "2024-03-01 00:00:00"
      }
    },
    {
      "table": "apm_project_initiation",
      "data": {
        "id": 10,
        "doc_id": "init_001",
        "start_time": "2024-01-05 00:00:00",
        "end_time": "2024-03-10 00:00:00"
      }
    }
    // ... 更多记录
  ]
}
```

#### 阶段二：执行时间更新

**函数**: `execute_update(offset_days)`

**执行步骤**：

1. 读取 `time_snapshot_before.json` 快照文件
2. 用户输入 `YES` 确认执行
3. 遍历每条记录，对时间字段加上 `offset_days` 天的偏移量
4. 生成 UPDATE SQL 并执行
5. 同时写入审计日志 `time_update_audit_log.jsonl`
6. 全部成功后提交事务，出错则回滚

**审计日志格式** (`time_update_audit_log.jsonl`)：

每行一条 JSON 记录，格式如下：

```
{
  "update_time": "2024-01-10 11:00:00",
  "table": "apm_project_requirement",
  "record_id": 1,
  "changes": {
    "request_time": {
      "before": "2024-01-01 00:00:00",
      "after": "2024-01-06 00:00:00"
    },
    "approve_time": {
      "before": "2024-01-02 00:00:00",
      "after": "2024-01-07 00:00:00"
    },
    "start_time": {
      "before": "2024-01-01 00:00:00",
      "after": "2024-01-06 00:00:00"
    },
    "end_time": {
      "before": "2024-03-01 00:00:00",
      "after": "2024-03-06 00:00:00"
    }
  }
}
```

### 5.7 修改前后记录保存机制

#### 快照文件（修改前）

- **文件**: `time_snapshot_before.json`
- **内容**: 所有待修改记录的原始值
- **用途**:
  - 执行前人工检查数据是否正确
  - 出错时可用于回滚恢复
  - 作为审计依据

#### 审计日志（修改前后对比）

- **文件**: `time_update_audit_log.jsonl`
- **内容**: 每条记录的每个时间字段的 `before` 和 `after` 值
- **格式**: JSON Lines，每行一条记录
- **用途**:
  - 精确追溯每个字段的变更
  - 支持按表、按记录 ID 查询变更历史
  - 可作为数据恢复的依据

#### 回滚方案

如需回滚，可基于审计日志中的 `before` 值生成反向 UPDATE SQL：

```
# 回滚示例代码
for log_line in audit_log_lines:
    log = json.loads(log_line)
    table = log["table"]
    record_id = log["record_id"]
    set_clauses = []
    for field, change in log["changes"].items():
        set_clauses.append(f"{field} = '{change['before']}'")
    sql = f"UPDATE {table} SET {', '.join(set_clauses)} WHERE id = {record_id}"
    # 执行回滚 SQL
```

### 5.9 注意事项

1. **issue_time 字段**: `apm_doc_main` 表的 `issue_time` 为 `varchar` 类型，脚本会尝试解析为日期，解析失败则跳过
2. **日期格式**: 脚本支持 `YYYY-MM-DD HH:MM:SS` 和 `YYYY-MM-DD` 两种格式
3. **事务安全**: 使用 `autocommit=False`，全部成功后手动 `commit()`，出错自动 `rollback()`
4. **备份建议**: 执行前建议先备份数据库，或确保快照文件完整可用
